## 3. 本次完成的诊断功能

### 3.1 启动前诊断

新增文件：

```text
src\NPMC.Launcher.App\Diagnostics\LaunchDiagnostics.cs
src\NPMC.Launcher.App\Diagnostics\LaunchLogSession.cs
```

实例概览顶部会出现诊断卡片，覆盖：

- 版本未安装
- Java 运行时问题
- 启动条件不满足
- 启动异常
- 异常退出后的日志分析

### 3.2 每次启动独立归档

每次真正启动游戏时创建：

```text
<launcher-root>\logs\launches\<yyyyMMdd-HHmmss>-<实例名>\
  launch.json
  README.txt
  latest.log
  nmpc-stderr.log
  nmpc-stdout.log
  nmpc-command.txt
  crash-reports/        # 仅当本次生成原生 crash-report
  crash.log             # 异常时生成的可读汇总
  result.json           # outcome=normal/crash、exit_code
  diagnosis.txt
```

关键行为：

- `latest.log` 仍是 Minecraft 的活动日志；
- 退出时复制到会话目录，按本次启动时间过滤；
- 诊断读取会话快照（`AnalyzeSession`），不读实例目录里可能过期的 live 文件；
- 正常会话保留最近 10 次，异常会话保留最近 50 次；
- 没有原生 crash-report 时不创建空的 `crash-reports`；
- `README.txt` 解释各文件；
- `crash.log` / `diagnosis.txt` 使用 UTF-8 BOM。

### 3.3 崩溃诊断规则

`LaunchDiagnostics.cs` 当前覆盖：

- 缺少前置模组
- 模组重复
- Mixin 冲突（仅真正 fatal，不再把可选兼容目标的 WARN 当冲突）
- Java 版本
- 内存不足
- 图形/OpenGL
- 登录凭据
- 文件缺失/损坏
- jar 损坏
- 模组加载失败
- `NoClassDefFoundError`
- Mixin 版本不兼容

结构化解析：

- crash-report 的 `-- MOD ... --`
- `Mod File:`
- `Failure message:`
- `Currently, ... is not installed`
- `Mixing ... from mixins.xxx.json into ...`
- `Class version ... required ... Mixin supports ...`

### 3.4 详细诊断启动

诊断卡片按钮：

```text
详细诊断启动
```

会追加：

```text
-Dmixin.debug=true
-Dmixin.debug.verbose=true
-Dmixin.debug.export=true
-Dmixin.checks.interfaces=true
-Dforge.logging.mixin.debug=true
```

并额外归档：

- `.mixin.out/`
- `logs/debug.log`
- `hs_err_pid*.log`

然后用户可点“查看崩溃日志”打开 `crash.log`，或“导出日志”生成 ZIP。

## 10. 2026-11-09：支持 MultiMC / Prism / HMCL 整合包导入

### 10.1 背景

用户拿到的「自然需求整合包[1.21.11]-V4.0..zip」（181.7 MB）是 HMCL 用 **MultiMC 格式**导出的：
`instance.cfg` + `mmc-pack.json` + `.minecraft/` 全量载荷（99 个模组、11 个资源包、2 个光影、servers.dat）。
原来的导入只认 mrpack 与 CF manifest，这类包落在 Unknown 分支，直接报"无法识别的整合包"。

### 10.2 实现

- `ModpackArchiveFormat.MultiMc`：`mmc-pack.json` 或 `instance.cfg` 即判定；
- `MultiMcPackManifest`：解析组件（`net.minecraft` / `net.fabricmc.fabric-loader` /
  `org.quiltmc.quilt-loader` / `net.neoforged` / `net.minecraftforge`）+ `instance.cfg`
  （name / MaxMemAlloc·MinMemAlloc / MinecraftWinWidth·Height）；
  载荷目录兼容 `.minecraft/` 与 `minecraft/`；
- `ModpackPlan.PackedPayload`：这类包没有下载清单，`InstallIntoAsync` 走"解压载荷"分支
  （zip-slip 校验、跳过包根的 `mmc-pack.json` / `instance.cfg` / `.packignore`）；
- 窗口尺寸与推荐内存写进新实例设置（实测包：2048 MB / 1600×900）。

**加载器版本严格按包内 mmc-pack.json，不做"就近回退"** —— 用户明确要求：
换版本可能踩到模组不兼容。装不上（官方没有该版本）就明确报错。

### 10.3 验证（用真实包，临时 root，未触碰 E: 数据）

```
用时 76 s：解析 → 装 MC 1.21.11 本体 → 装 fabric-loader 0.18.4 → 解压 329 个文件
实例：331 个文件 / mods 99 个 / 版本 fabric-loader-0.18.4-1.21.11
设置：memory 2048 MB，窗口 1600×900
启动计划：jvmArgs 14、gameArgs 24、classpath 68（只差 Java 运行时，临时 root 本来就没有）
```

用例 7 个（`MultiMcPackTests`）：格式识别、严格版本解析（含 net.minecraft 重复两次）、
Prism 的 `minecraft/` 载荷、组件 uid 映射、缺 net.minecraft 拒绝、解压跳过元数据、zip-slip 拒绝。
Core 400/400、App 31/31。

### 10.4 分发格式调研结论（2026-11-09）

| 格式 | 识别文件 | 我们 |
| --- | --- | --- |
| Modrinth `.mrpack` | `modrinth.index.json`（+ overrides / client-overrides / server-overrides） | ✅ |
| CurseForge `.zip` | `manifest.json` | ✅（需 CF API key） |
| MultiMC / Prism / HMCL | `mmc-pack.json` + `instance.cfg` | ✅（本轮） |

## 11. 2026-11-09：内存设置与整合包预设的关系（用户反馈修正）

「Fabulously Optimized」开着自动、内存框却写 4096，只有下面一行小字写「自动：5120 MB」。

### 11.2 两个根因

1. **MMC 包把 `MinMemAlloc` 当成了推荐内存**：这类包的 instance.cfg 常只写 `MinMemAlloc=2048`
   （作者的最低要求），原实现 `MaxMemAlloc ?? MinMemAlloc` 把它当"推荐值"，
   于是安装时强制手动 2048 并把自动关掉。现在只认 `MaxMemAlloc`。
2. **整合包预设会覆盖用户的「自动内存」选择**，而概览页的内存框在自动模式下显示的是
   存储值（4096）而不是自动算出来的值（5120），看起来就像自动没生效。

### 11.3 规则（用户选定：折中）

- 用户勾了自动 → **保持自动**，整合包预设值变成自动值的**下限**（`InstanceSettings.MemoryFloorMb`）：
  自动算出比它小就用它兜底；空闲内存不足时仍会被容量上限压回去。
- 用户是手动模式 → 直接按作者推荐值（与以前一致）。
- 概览页内存框在自动模式下显示**自动算出来的值**（`EffectiveMemoryMb`），不再显示存储值。

### 11.4 验证

临时 root + 真实 MMC 包（99 个模组）安装，全局设为自动内存：

```
实例设置：memoryMb=4096  autoMemory=true  memoryFloorMb=0
列表显示：自动 6144 MB
摘要不再出现"推荐内存 2048 MB"
```

用例 +5：预设保留自动并记为下限 / 手动模式按预设 / 下限抬高自动值 /
下限不降低自动值 / 空闲内存仍能压住下限；另加 MMC「只写 MinMemAlloc 不算推荐值」。

## 13. 2026-11-09：翻译缓存改成「CSV + 元数据 JSON」

### 13.1 原来的问题

`<root>\data\cache\translations\` 是「每条译文一个 `<sha1>.txt`」：文件名是哈希、内容只有译文，
**没有原文** —— 既看不出对应哪段文字，也没法校对、导出或手工改（实测 7 个文件全是黑盒）。

### 13.2 新结构（用户选择：CSV + 纯元数据 JSON）

```
<root>\data\cache\translations\translations.csv   ← 唯一数据源，可直接用 Excel 打开
<root>\data\cache\translations\meta.json          ← schema / 条目数 / 最后整理时间（不参与查找）
```

CSV 列：`key,lang,source,translated,updatedAt`（`key = sha1(lang|source)`，与旧文件名规则一致）。

要点：

- **不存 key→行号 索引**：手改 CSV 后行号会错位，查找一律用启动时读进内存的记录表；
- CSV 用 UTF-8 **带 BOM**（Excel 中文不乱码）、RFC 4180 转义（原文里的逗号/引号/换行都不会拆行）；
- 写入是追加；每 200 条或超 5000 条时整体重写（先写 `.tmp` 再原子替换），按时间保留最近的；
- 读到的 CSV 没有表头/结构坏了 → 标记 `_needsRewrite`，下次写入前整体重写，不在坏文件后面接着追加；
- **旧 `.txt` 懒迁移**：命中该条时能拿到原文 → 补一行进 CSV → 删掉旧文件（哈希不可逆，事先无法批量重建）。

### 13.3 验证

用例 5 个（`TranslationCacheTests`）：含逗号/引号/换行的往返、元数据 JSON、同 key 覆盖、
旧文件懒迁移、坏 CSV 回退重写。Core 410/410、App 31/31。

## 15. 2026-11-09：翻译端点限流 → 三点回退链；CSV key 改哈希

### 15.1 现象与真因

用户反馈"图 2 的译文没出现"，同时 CSV 里只有一行。实测：

```
GET https://translate.googleapis.com/translate_a/single?...  → HTTP 429 Too Many Requests
```

**不是缓存改造的问题，是 Google 的公共 gtx 端点把本机限流了**。
旧实现遇到任何失败都静默返回 null，界面只显示原文，所以看起来像"翻译功能坏了"。

### 15.2 改动

1. **三点回退链**（每个端点各自 10 分钟冷却，429/403 才冷却）：
   - gtx（`translate_a/single`，质量最好、最容易被限流）
   - `clients5.google.com/translate_a/t?client=dict-chrome-ex`（实测 200 可用）
   - MyMemory 免费接口（**必须显式源语言**，不支持 auto；按字符集猜 en/ja/ko/ru，
     按 450 字切段拼接，并识别它用"译文"字段返回的错误提示，避免把报错写进缓存）
2. **失败不再完全静默**：端点名/状态码写进 `logs/launcher.log`；连续限流时冷却期内直接跳过，避免越点越久。
3. **CSV 的 key 改成 sha1**：之前把 `"语言|原文"` 整段当 key 写进 CSV（Excel 里一格塞满原文）。
   现在 key = `sha1(语言|原文)`，与旧版 `.txt` 文件规则一致；读到带 `|` 的旧行会自动改写成哈希。
4. 新增诊断：`--exercise-translation <文本>` 直接打印译文/冷却状态/缓存路径。

### 15.3 验证


## 16. 2026-11-09：长正文分段翻译；新增 Bing（微软）端点

### 16.1 现象

用户截图：长简介只有前半段被翻译，后半段仍是英文。

### 16.2 原因与修法

端点对单次请求长度有限制，**超长时不会报错，而是只翻前面一部分**。所以：

- 正文统一切成 ≤900 字的小段（优先在空格/换行处断开，日文这类无空格文本也有断点），
  逐段走回退链再拼接；最多 6 段（5400 字），超出部分不翻；
- 只有**整段都翻成功**才写缓存；翻到一半失败时会在末尾加「…（后文未翻译）」并且不落盘，
  避免半截译文被永久缓存。

### 16.3 新增 Bing 端点（不需要 API key）

微软的网页版翻译通道：

1. `GET https://www.bing.com/translator` → 解析 `IG` / `data-iid` /
   `params_AbusePreventionHelper = [key, token, lifetimeMs]`；
2. `POST https://www.bing.com/ttranslatev3?isVertical=1&&IG=..&IID=..`
   （表单：fromLang=auto-detect、to=zh-Hans、text、token、key）；
3. token 约 10 分钟有效，缓存在内存里，过期或 400 时自动重抓。

回退顺序：gtx → **Bing** → dict-chrome-ex → MyMemory（各自 10 分钟冷却）。

### 16.4 验证

1239 字的样例文本（长简介）：

```

译文全文为中文，无「后文未翻译」标记，已写入 CSV
```

## 17. 2026-11-09：翻译改成「按需触发」+ 本地小时配额

### 17.1 为什么改

公共翻译端点（gtx / Bing 网页版 / dict-chrome-ex / MyMemory）都按 IP 软限流，额度不公开。
原来点开任意模组详情就会自动请求，浏览一遍列表能打出上百个请求，很快被限流
（用户实测 gtx 已经 429，且要等很久才恢复）。

### 17.2 改法

1. **打开详情只查缓存**（`TranslationClient.TryGetCached`）：
   命中就直接显示译文；没命中时显示「机翻这段简介」按钮，用户点一下才真正请求。
   同一段简介翻过一次后走缓存，不会再请求。
2. **本地小时配额**：每小时最多 120 个真实请求（含 Bing 令牌抓取），
   超出后只用缓存并写一条日志；这是为了防止把 IP 打进黑名单，不是硬性服务端限制。
3. 按钮状态：`CanTranslateDetail` 依赖正文/译文/是否在翻，正文变化与译文变化都会刷新。

### 17.3 验证

用例 +3（`TranslationClientCacheTests`：缓存命中不出网、未命中返回 false、超长文本截断一致）。
Core 417/417、App 35/35。
